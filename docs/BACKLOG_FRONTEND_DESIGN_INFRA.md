# Backlog — frontend, инфраструктура и дизайн

## Инфраструктура перед production

### INFRA-01. Выбрать и подключить CDN
**Статус:** planned  
**Приоритет:** high  
**Зависимости:** определиться с хостингом frontend/backend и целевой географией аудитории.

Задачи:
- Сравнить CDN-провайдеров по географии PoP, задержкам для основной аудитории, цене, TLS, DNS, purge API, логам, защите от DDoS/WAF и поддержке нужных cache rules.
- Определить, что именно проходит через CDN: frontend static assets, публичные GET API и, если это разрешено условиями поставщика, картографические тайлы.
- Настроить домен, DNS, TLS и маршрутизацию к origin.
- Для Vite assets с content hash установить долгий immutable Cache-Control.
- Для HTML установить короткий TTL/no-cache, чтобы клиенты получали актуальный entry point.
- Для публичных GET API определить cache key, TTL, stale-while-revalidate, purge/invalidation и защиту от кеширования персональных/модераторских ответов.
- Исключить из shared cache все mutation-запросы, moderator endpoints, ответы с Authorization/cookies и ошибки, если отдельная политика не согласована.
- Настроить bypass и корректные Cache-Control/Vary для динамических ответов.
- Проверить cache HIT/MISS, purge, корректность CORS и отсутствие утечек между разными query-параметрами.

**Критерии готовности:**
- CDN-провайдер выбран и решение записано с обоснованием.
- DNS/TLS и origin настроены.
- Правила кеширования задокументированы и проверены на публичных GET.
- Модераторские и изменяющие данные запросы не попадают в shared cache.
- Есть процедура purge и инструкция эксплуатации.

### INFRA-02. Выбрать картографического провайдера и подключить API-ключи
**Статус:** planned  
**Приоритет:** high  
**Зависимости:** выбор провайдера карт; проверка тарифов, лимитов, лицензии и условий кеширования/атрибуции.

Задачи:
- Сравнить картографических провайдеров по покрытию нужного региона, качеству тайлов, стилям, геокодированию (если потребуется), лимитам, тарифам и условиям использования.
- Проверить требования к attribution, хранению/кешированию тайлов и допустимому использованию через CDN.
- Определить тип ключа: публичный browser key с ограничением по доменам/referrer и API scopes либо секретный server-side key, если провайдер поддерживает безопасный proxy flow.
- Не помещать секреты в VITE_* и frontend bundle: все такие значения доступны посетителю сайта.
- Хранить серверные секреты в environment variables/secret manager на backend/origin; публичный ограниченный ключ хранить в frontend config только если это предусмотрено моделью безопасности провайдера.
- Настроить ограничения ключей по доменам, API, квотам и окружениям (development/staging/production).
- Настроить ротацию ключей, мониторинг квот и оповещение о превышении лимитов.
- Подключить выбранный источник тайлов к OpenLayers и добавить обязательную атрибуцию.

**Критерии готовности:**
- Провайдер и тарифная модель выбраны, ограничения и лицензия задокументированы.
- Ключи не раскрывают серверные секреты и ограничены по домену/API/квотам.
- Тайлы отображаются в production, attribution присутствует.
- Описаны ротация ключей и действия при утечке/превышении квоты.

## Отложенные задачи Backend — hardening и приёмка

> Добавлено после статического аудита Backend-ТЗ v1.0. Не блокирует переход к следующему этапу разработки; выполнить отдельным проходом перед финальной приёмкой/production.

### BACKEND-01. Усилить валидацию CORS-конфигурации
**Статус:** planned  
**Приоритет:** high

- Запретить wildcard `*` в `CORS_ORIGINS`, особенно при `allow_credentials=true`.
- Проверять конфигурацию при старте приложения и выдавать понятную ошибку при небезопасных значениях.
- Убедиться, что разрешены только явно перечисленные frontend origins.

**Критерий готовности:** приложение не стартует с небезопасной CORS-конфигурацией; корректный список origin работает с credentials.

### BACKEND-02. Унифицировать обработку непредвиденных ошибок
**Статус:** planned  
**Приоритет:** medium

- Проверить обработчик необработанных исключений.
- Возвращать согласованный JSON-формат `{ "code": "...", "detail": "..." }` для HTTP 500.
- Не раскрывать клиенту traceback, SQL, внутренние пути и секреты.
- Сохранять подробности ошибки только в серверных логах с безопасной фильтрацией.

**Критерий готовности:** контролируемая тестовая 500-ошибка возвращает единый формат без внутренних деталей.

### BACKEND-03. Дополнить OpenAPI-документацию Audit Log
**Статус:** planned  
**Приоритет:** low

- Добавить документированные ответы 401 и 403 для `GET /moderator/audit-logs`.
- Сверить OpenAPI-коды ответов остальных защищённых маршрутов с реальным поведением.

**Критерий готовности:** Swagger показывает ожидаемые ошибки авторизации и доступа.

### BACKEND-04. Обеспечить регистронезависимую уникальность названий категорий
**Статус:** planned  
**Приоритет:** medium

- Проверить текущие ограничения уникальности `categories.name` и `slug`.
- При необходимости добавить миграцию с уникальным индексом по `lower(name)`.
- Проверить конфликтующие варианты регистра и пробелов; сохранить существующие данные.

**Критерий готовности:** категории с одинаковым названием в разном регистре не могут быть созданы.

### BACKEND-05. Расширить интеграционное покрытие Backend
**Статус:** planned  
**Приоритет:** high

- Добавить интеграционные тесты с PostgreSQL/PostGIS и HTTP-клиентом.
- Покрыть CRUD категорий и точек, фильтры, архивирование/восстановление.
- Покрыть жизненный цикл заявок, approve/reject, повторную обработку и атомарность создания точки.
- Проверить авторизацию, CSRF, CORS, единый формат ошибок и Audit Log.
- Сохранить изоляцию тестовой БД от рабочей базы.

**Критерий готовности:** ключевые критерии Backend-ТЗ проверяются автоматизированными интеграционными тестами.
